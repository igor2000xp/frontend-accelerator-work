# Frontend Accelerator Toolset

Нативный фронтенд-воркфлоу для агентов и зафиксированная среда выполнения инструментов (Runtime Toolchain) для существующих TypeScript-репозиториев. Он добавляет каталог ручной доставки, изолированных агентов, переиспользуемые навыки, заменяемые правила лучших практик, автоматизацию реального браузера и портативный линт-ограничитель для измененных файлов, не меняя фреймворк приложения, структуру исходников, зависимости, скрипты или корневые инструкции.

Это не стартовый шаблон React, не генератор проектов, не оркестратор, не пайплайн управления, не бэкенд-воркфлоу и не глобальный CLI-пакет. React является лишь дефолтным набором правил фреймворка (Framework Ruleset) и может быть заменен.

## Обучение (Training)

Все материалы по онбордингу и оценке находятся в директории [`training/`](https://www.google.com/search?q=training/README.md). Новым участникам следует начинать с этой единой точки входа.

## Предварительные требования (Prerequisites)

* Node.js 24 или новее для CLI акселератора и управляемых инструментов. Целевое приложение может указывать более старую версию Node.js.
* Git, при этом команды должны запускаться из корневой директории Git целевого репозитория.
* Сетевой доступ нужен только для `setup`, если зафиксированные артефакты еще не закешированы.

## Установка дистрибутива проекта (Install The Project Payload)

Рекомендуемый установщик перед записью выводит предварительный просмотр каждой операции копирования и конфигурации хуков:

```powershell
npx github:<org>/<repo> install

```

Для локального репозитория, включая пути с пробелами:

```powershell
npx --package "C:\path with spaces\frontend-accelerator-toolset" frontend-accelerator install

```

Установщик копирует следующие принадлежащие проекту директории:

```text
.claude/
.agents/
rulesets/
toolchain/

```

Обычные файлы полезной нагрузки только копируются. Любая точная коллизия целевого пути фиксируется и выводится до подтверждения, при этом запись не производится.

Единственным исключением для объединения являются файлы `.claude/settings.json` и `.codex/hooks.json`. Установщик сохраняет не относящиеся к делу настройки и хуки, единоразово добавляет распознанные регистрации акселератора и считает невалидный JSON или измененную регистрацию с идентификатором акселератора конфликтом. Точный устаревший лаунчер Codex для Windows, который вкладывал `powershell.exe -Command`, распознается для последующего обновления; никакие другие смысловые отклонения не допускаются. Успешная установка записывает `.frontend-accelerator/installation.json` с SHA-256 дайджестом каждого установленного файла. Установщик никогда не редактирует зависимости приложения, локфайлы приложения, исходный код, корневые `AGENTS.md`, `CLAUDE.md`, глобальный PATH или доверие среды выполнения.

Используйте `--yes` только после проверки той же операции в интерактивном режиме, если требуется неинтерактивная установка.

## Обновление существующей установки (Update An Existing Installation)

Используйте явную команду обновления вместо повторного запуска `install` поверх существующих директорий полезной нагрузки:

```powershell
npx github:<org>/<repo> update

```

Для локальной рабочей копии акселератора:

```powershell
npx --package "C:\path with spaces\frontend-accelerator-toolset" frontend-accelerator update

```

Обновление проверяет каждый существующий файл акселератора по квитанции об установке перед его заменой или удалением. Файл, измененный после установки, фиксируется как конфликт и отменяет любые операции записи. Новые файлы копируются, неизмененные переиспользуются, сторонние файлы проекта и конфигурация среды выполнения сохраняются, а распознанные регистрации хуков объединяются отдельно.

Установки, созданные до появления квитанций, инициализируются только в том случае, если их измененные файлы совпадают с явно распознанной устаревшей версией акселератора. Это поддерживает миграцию с релиза с вложенным лаунчером Codex Windows PowerShell без считывания произвольного содержимого как принадлежащего акселератору.

Если обновление меняет команды хуков, просмотрите и подтвердите их доверие заново через `/hooks`, затем начните новую сессию, чтобы `SessionStart` мог записать актуальное подтверждение активации. Используйте `update --yes` только после интерактивной проверки плана обновления.

### Ручная установка (Manual installation)

Четыре директории полезной нагрузки по-прежнему можно скопировать вручную. При ручной установке необходимо также объединить логические регистрации из `toolchain/registrations/claude-hooks.json` и `toolchain/registrations/codex-hooks.json` с соответствующими настройками проекта. Не заменяйте существующий документ настроек полностью. `frontend-accelerator doctor` будет выводить статус `NOT_CONFIGURED` до тех пор, пока текущие регистрации не будут добавлены.

## Развертывание среды выполнения инструментов (Provision The Runtime Toolchain)

Установка записывает файлы проекта, но не выполняет скачиваний. Развертывание (provisioning) — это отдельная команда, требующая явного подтверждения:

```powershell
npx github:<org>/<repo> setup

```

Для локального репозитория акселератора:

```powershell
npx --package "C:\path with spaces\frontend-accelerator-toolset" frontend-accelerator setup

```

Setup устанавливает точные версии из манифеста в пользовательский кэш, принадлежащий акселератору:

| Возможность | Требование | Фиксированная версия |
| --- | --- | --- |
| Реальный браузер | Обязательно | `agent-browser@0.32.3` |
| Актуальная документация библиотек | Рекомендуется | `ctx7@0.5.5` |

Транзакция установки проверяет целостность npm lock, записывает точку входа пакета и управляемый исполняемый файл Chrome в квитанцию, атомарно повышает статус каждой возможности и сохраняет работоспособный обязательный браузер, если рекомендуемая настройка Context7 завершается с ошибкой. Doctor разрешает записанный путь к Chrome и отклоняет отсутствующий артефакт или тот, который выходит за пределы выбранного кэша возможностей. Setup не запускает менеджер пакетов в целевом приложении и не добавляет управляемые исполняемые файлы в глобальный PATH.

`agent-browser@0.32.3` не предоставляет параметр выбора директории установки. Поэтому Setup импортирует версию Chrome, созданную его установщиком, в локальный промежуточный кэш возможности (staging) и запускает адаптер только с путем к управляемому исполняемому файлу. Директория версии Chrome, созданная текущей транзакцией установки, удаляется после успешного завершения; любые ранее существовавшие скачивания в `~/.agent-browser` остаются нетронутыми.

Корневые директории кэша по умолчанию: `%LOCALAPPDATA%\frontend-accelerator` в Windows, `~/Library/Caches/frontend-accelerator` в macOS и `$XDG_CACHE_HOME/frontend-accelerator` или `~/.cache/frontend-accelerator` в Linux. Переменная `FRONTEND_ACCELERATOR_CACHE_DIR` позволяет явно переопределить путь для CI/тестов. Записи изолированы по хэшу манифеста, ОС и архитектуре.

Если процесс setup был прерван или квитанция стала недействительной, запустите `setup` повторно. Исправные компоненты переиспользуются, незавершенная подготовка никогда не задействуется, а невалидный компонент пересобирается без удаления других исправных компонентов. CLI намеренно не содержит общих команд очистки кэша; записи кэша восстановимы и могут быть удалены вручную только после определения точного пути, указанного Doctor.

Для неинтерактивной настройки используйте `setup --yes` только после того, как проверите аналогичный предпросмотр в интерактивном режиме. Отклоненные команды `install`, `update` или `setup` завершаются успешно, не внося никаких изменений. Некорректное использование и операционные ошибки завершаются с кодом `1`; команда `setup` также завершается с кодом `1`, если обязательный компонент заблокирован.

## Диагностика готовности (Diagnose Readiness)

Команда Doctor работает только в режиме чтения: она никогда не устанавливает, не ремонтирует, не очищает, не подтверждает доверие и не перезаписывает состояние.

```powershell
frontend-accelerator doctor
frontend-accelerator doctor --json

```

Эквивалент внутри проекта доступен, даже если CLI пакета отсутствует в PATH:

```powershell
node ./toolchain/bin/doctor.mjs --json

```

Результаты верхнего уровня:

* `READY`: обязательные инструменты, рекомендуемые инструменты, активация хуков и возможности линтера доступны.
* `DEGRADED`: обязательный браузер присутствует, но рекомендуемая возможность или сигнал ограничителя неполны.
* `BLOCKED`: проверка Node/манифеста, готовность обязательного браузера или конфигурация хуков недействительны.

Подстатусы хуков различают `NOT_CONFIGURED`, `PENDING_ACTIVATION`, `ACTIVE` и `STALE`.

Doctor завершается с кодом `0` как для статуса `READY`, так и для `DEGRADED`, поэтому рекомендуемые возможности и ограничения защитного барьера остаются видимыми, не ломая автоматизацию. Он завершается с кодом `1` только при статусе `BLOCKED`.

## Проверка и активация хуков (Review And Activate Hooks)

Claude Code и Codex требуют, чтобы хуки проекта были проверены через их собственный процесс подтверждения доверия (trust flow). Установщик никогда не предоставляет и не обходит доверие.

После установки начните новую сессию в целевом репозитории и откройте `/hooks`. Проверьте четыре события акселератора: `SessionStart`, `PreToolUse`, `PostToolUse` и `Stop`. Как только доверенный `SessionStart` выполнится, он запишет подтверждение активации хука (Hook Activation Proof) в кэш акселератора; затем Doctor изменит статус этой среды выполнения с `PENDING_ACTIVATION` на `ACTIVE`. Изменение манифеста или регистрации делает старое подтверждение `STALE` до тех пор, пока не выполнится новый хук.

`PreToolUse` записывает исходное состояние для файлов, указанных инструментом, или снапшот рабочего дерева, если команда оболочки не идентифицирует свои файлы. Соответствующий `PostToolUse` сравнивает состояния «до» и «после» и связывает созданные, измененные, удаленные и переименованные пути с текущей сессией. Ранее измененные файлы исключаются, если их содержимое не меняется во время вызова инструмента. Если пару не удается сопоставить, защитный барьер сообщает об ухудшении атрибуции вместо того, чтобы гадать.

Хук Stop запускает один существующий скрипт `lint` проекта для файлов, относящихся к текущей сессии агента. Он никогда не устанавливает зависимости и не применяет автоисправления. Ошибка линтера запрашивает одно продолжение; неизменный повторный запуск Stop сообщает о записанной ошибке без повторного запуска или зацикливания. Отсутствующая или неоднозначная возможность линтинга означает явный статус `DEGRADED`, а не ложное прохождение.

## Настройка среды выполнения агентов (Agent Runtime Setup)

Claude напрямую использует закоммиченные файлы `.claude/commands`, `.claude/agents` и `.claude/skills`. Вызовите одну из именованных команд, например `/requirements-analyst` или `/coder`.

Codex использует то же содержимое навыков из `.agents/skills`. Сгенерированные определения агентов находятся в `.agents/codex-agents.toml`; объедините или включите эти определения в пользовательскую конфигурацию Codex с помощью механизма, поддерживаемого установленной версией Codex, затем включите поддержку нескольких агентов (multi-agent support). Набор инструментов не редактирует глобальную конфигурацию Codex.

Обе среды выполнения следуют единой модели воркфлоу:

```text
пользователь вызывает команду -> изолированный агент вызывает один навык -> агент предоставляет доказательства и делает STOP

```

Агент может порекомендовать контекстную следующую команду, но никогда не запускает её самостоятельно.

## Наборы правил (Rulesets)

Правила остаются нейтральными к среде выполнения и разделены на три заменяемых уровня:

```text
rulesets/common/      нейтральные к фреймворку практики фронтенда
rulesets/framework/   специфичные для фреймворка практики; React по умолчанию
rulesets/project/     соглашения проекта, принадлежащие команде

```

Агенты разрешают правила через файлы `INDEX.md`, специфичные для ролей. Отсутствие необязательных разделов допустимо. Набор инструментов не генерирует `.claude/rules/` и не выводит политику проекта из исходного кода.

Чтобы заменить React, удалите или архивируйте специфичное для React содержимое в `rulesets/framework/`, добавьте правила нового фреймворка и обновите соответствующие индексы ролей. Стандартные правила React являются зафиксированными снимками из источника с прилегающими метаданными.

## Проверка в браузере (Browser Verification)

`browser-verify` сначала запускает Doctor проекта, а затем использует только:

```powershell
node ./toolchain/bin/agent-browser.mjs --session <name> <command>

```

Он определяет фактический URL приложения, запрашивает подтверждение перед запуском сервера разработки и останавливает только тот сервер/сессию, которыми владеет. Последовательность сбора доказательств охватывает область просмотра (viewport), снимки доступности, взаимодействия, консоль, ошибки страницы, сетевые запросы и скриншоты при необходимости. Запасных вариантов вроде Playwright CLI или глобального `agent-browser` нет.

Технические роли используют `node ./toolchain/bin/ctx7.mjs library ...` с последующим `docs ...`, когда решение существенным образом зависит от актуальной сторонней документации. Отсутствие Context7 является признаком ухудшения доказательной базы, а не разрешением придумывать API.

### Отложенные возможности (Deferred capabilities)

Текущая среда выполнения инструментов намеренно не развертывает RTK, CodeGraph или Graphify. Переписывание команд RTK требует отдельного межплатформенного контракта и может скрывать диагностический контекст; индексация кода требует собственного дизайна хранения, конфиденциальности, регистрации MCP и владения хуками. Playwright CLI также не поставляется в качестве второго провайдера браузера: проверка в браузере использует только зафиксированный адаптер `agent-browser`, принадлежащий проекту.

## Статус проверки (Verification Status)

Автоматизированные тесты охватывают валидацию манифеста, разрешение кэша платформы, атомарное поведение установки, обновления установок на основе квитанций и устаревших версий, состояния Doctor только для чтения, безопасные объединения хуков, атрибуцию файлов текущей сессии, подавление зацикливания линтера, контракты навыков, целостность каталога/наборов правил и паритет сгенерированного Codex. Настроенная матрица CI запускает тестовый набор тестового установщика на Node.js 24 в Windows, Linux и macOS без скачивания браузера. Текстовые файлы репозитория нормализованы до LF через `.gitattributes`; проверки владения путями и кэшем канонизируют физические пути, чтобы соединения директорий Windows и псевдонимы коротких путей не выказывали ложных сбоев границ кэша.

Смоук-тестирование в реальном времени на Windows подтвердило одноразовую установку, повторное использование кэша, обе проверки возможностей и последовательность работы управляемого браузера `open about:blank` -> `snapshot` -> `close`. Доказательства релиза по-прежнему требуют облачного CI для Linux/macOS, а также одной сессии Claude Code и Codex на стороне хоста, которая доверяет регистрациям, меняет статус Doctor с `PENDING_ACTIVATION` на `ACTIVE` и единоразово запускает существующий скрипт линтинга при Stop.

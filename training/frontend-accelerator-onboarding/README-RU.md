# Basic Accelerator Onboarding (Базовое погружение)

Это основной учебный трек для тех, кто впервые использует Frontend Accelerator.

Не используйте файлы из директории `frontend-accelerator-assessment/` во время выполнения этой задачи. Там находится отдельная продвинутая оценка для продакшена (Advanced / Production Assessment).

## Цель

Научиться проводить одну небольшую задачу по фронтенду через ручной рабочий процесс (workflow) акселератора:

```text
разработчик выбирает роль
-> изолированный агент выполняет один навык (skill)
-> агент предоставляет отчет и ОСТАНАВЛИВАЕТСЯ (STOP)
-> разработчик проверяет результат и выбирает следующую роль

```

Успешное прохождение означает контроль и проверку рабочего процесса. Это не означает создание полностью готового к продакшену приложения.

Разработчик также должен самостоятельно сформулировать базовый, четко ограниченный промпт для каждой выбранной роли. Это погружение не предоставляет готовых промптов для копирования.

## Временные рамки (Timebox)

На активную работу отводится до шести часов. Первоначальная установка окружения в этот лимит не входит.

Прекратите расширять функциональность (scope), как только заработает требуемый пользовательский сценарий (user flow). Затратьте оставшееся время на ревью и верификацию.

## Перед началом работы

1. Используйте подготовленный репозиторий на React и TypeScript с установленным Frontend Accelerator.
2. Запустите Runtime Doctor один раз:
```powershell
node ./toolchain/bin/doctor.mjs --json

```


3. Зафиксируйте в `workflow-log.md` только верхнеуровневый результат работы Doctor и статус соответствующих хуков среды выполнения.
4. Прочитайте [`TASK.md`](https://www.google.com/search?q=TASK.md) и [`PASS_CRITERIA.md`](https://www.google.com/search?q=PASS_CRITERIA.md).

Отдельный отчет об установке (setup receipt) не требуется для сдачи базового погружения. Результат Doctor со статусом `BLOCKED` останавливает выполнение задания только в том случае, если он препятствует запуску рабочего процесса ролей.

## Обязательная последовательность ролей

Запускайте эти роли строго по одной за раз:

1. `requirements-analyst`
2. `writing-plans`
3. `coder`
4. `code-reviewer`
5. `verify`

После каждой роли:

1. запишите точный промпт, который вы использовали, в `workflow-log.md`;
2. прочитайте результат работы роли;
3. решите, принять ли его, уточнить или запросить исправление;
4. запишите принятое решение в `workflow-log.md`;
5. вручную выберите следующую роль.

Роль может порекомендовать следующее действие, но она не должна запускать другую роль автоматически.

Используйте роли `architect`, `api-integration`, `ui-designer`, `test-generator`, `debugger` или `browser-verify` только тогда, когда они действительно необходимы для задачи. Необязательные роли не влияют на итоговый результат прохождения.

## Как составлять промпт для роли

Напишите промпт для каждой роли самостоятельно, используя следующую структуру:

```text
Контекст и источники -> ограниченный результат -> ожидаемый артефакт или доказательства (evidence) -> важные ограничения -> СТОП (STOP)

```

Хороший промпт для базового погружения отвечает на пять вопросов:

1. **Какой контекст должна прочитать роль?** Укажите ID задачи, файл задачи, подтвержденный артефакт или ограниченный diff.
2. **Какой результат требуется?** Запросите один конкретный результат, входящий в зону ответственности этой роли.
3. **Куда сохранить итоговый результат?** Укажите артефакт задачи, если роли разрешено его записывать.
4. **Что роль делать не должна?** Укажите важное ограничение (например, запрет на правку исходного кода во время ревью или верификации).
5. **Где она должна остановиться?** Потребуйте от роли предоставить отчет о результате и ОСТАНОВИТЬСЯ (STOP) без запуска следующей роли.

Не просите одну роль выполнить весь цикл разработки. Не вставляйте инструкции по реализации до того, как появились требования и план. Промпт может быть коротким, если его контекст и границы остаются четкими.

Для роли `code-reviewer` (работающей в режиме только для чтения) сохраните полученный ответ дословно как `tasks/<task-id>/review.md`; не переписывайте её вердикт. Для `verify` явно запросите фактические команды, коды завершения (exit results), сбои и непроверенные пункты в `tasks/<task-id>/verification.md`.

## Ожидаемые артефакты

Роли акселератора должны создать или предоставить содержимое для следующих файлов:

```text
tasks/<task-id>/requirements.md
tasks/<task-id>/implementation-plan.md
tasks/<task-id>/review.md
tasks/<task-id>/verification.md
tasks/<task-id>/workflow-log.md

```

Разработчик не создает и не редактирует артефакты ролей вручную. Если роль с доступом «только для чтения» не может записать свой результат, сохраните её ответ в указанный файл дословно. Разработчик отвечает за проверку артефактов и за то, чтобы они содержали реальные результаты.

Начните вести `workflow-log.md` на основе шаблона [`workflow-log.template.md`](https://www.google.com/search?q=workflow-log.template.md). Ведите его лаконично: одной строки на вызов роли или важное решение разработчика будет достаточно.

## Что делать, если навык сработал некорректно

Не принимайте неверный или нерелевантный результат молча.

1. Объясните конкретную проблему той же роли один раз и запросите исправление.
2. Проверьте исправленный результат.
3. Если ограничение сохраняется, запишите его в `workflow-log.md` и продолжите работу, приняв разумное решение со стороны разработчика.

Выявление и исправление ошибок в работе агента — часть учебной цели.

## Формат сдачи работы

Предоставьте:

* рабочий репозиторий;
* артефакты задачи, перечисленные выше;
* команды и фактические результаты, записанные ролью `verify`;
* один короткий отчет о ручной проверке в браузере, покрывающий основной сценарий;
* известные ограничения, оставшиеся после ревью.

Публикация (deployment), публичный URL, pull request, настройка CI, полная матрица тестирования в браузерах или доказательства для продвинутой оценки (advanced assessment) не требуются.
